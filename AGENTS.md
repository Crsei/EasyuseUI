# EasyuseUI

## Project purpose and component-first examples

- EasyuseUI is a source-first component workshop: showcase simple primitives, build reusable complex components, then assemble realistic project examples. Examples validate component composition; they are not a mandate to implement every backend product here.
- Existing libraries and reference projects may provide the foundation. Inspect actual APIs/source, record origin/version/license and adaptation, and preserve attribution. Prefer proven interaction/rendering engines over rebuilding editors, charts, graphs, tables or drag-and-drop algorithms in page code.
- Before assembling or revising an example, inventory **all elements** and map each to an existing component, an extension, or a proposed component. Build/extend missing components first and mount the actual components together on a unified element showcase page; a list of names, screenshot or one-module selector is not the complete showcase.
- Keep two explicit, linked deliverables: **presentation** (working element showcase and assembled page, visual states and responsive behavior) and **design specification** (page/module declarations, tokens, dimensions, interactions, data/authority contracts and acceptance). Show specification/technology details in development showcases, not in ordinary product task flows.
- Pages and example adapters compose components and supply data/callbacks. Do not handcraft page-local CSS, inline visual styles or duplicated markup to impersonate a missing component. First implement the corresponding primitive/pattern/layout component. Component-owned Tailwind/CSS Modules, shared theme tokens and necessary calculated layout styles remain allowed; the rule forbids bypassing the component layer, not CSS itself.
- Each example plan and developer showcase must state the technologies actually used, the component/source mapping, why a dependency was added, loading boundaries, and the difference between installed, adopted and planned technologies. Reuse Next/React/TypeScript/Tailwind, Base UI/shadcn distribution and Lucide; adopt Zod, Query, Table, Recharts, Zustand, dnd kit, React Flow, editors and terminals where the module needs them. Do not install the entire stack or replace Base UI with Radix merely to match a list.
- Sequence: reference/source audit → page/module specification and stack declaration → components and unified element showcase → assembled page → mounted visual/interaction review → distribution and service checks appropriate to the change. Preserve existing behaviors while migrating; do not claim legacy examples already satisfy the new process.
- Agent Workspace's current migration and element/technology audit are in [component-first plan](./plans/agent-workspace-component-first-plan.md), linked from the existing [workspace plan](./plans/agent-workspace-plan.md). CW service milestones remain separate from visual/component delivery.

## Example design declarations — page and module

- Before designing or changing an example, record its applicable design principles and layout rules in that example's repository plan or design document. Link the reference, the formal contracts above and the actual reusable components. Use two levels: **page declarations** for the whole experience and **module declarations** for individual regions/elements. Do not rely on an image, a component name or “follow the design system” as the entire specification.
- For a **page**, declare: route/page ID; user goal and primary flow; information ownership and region hierarchy; default expanded/collapsed state; dimensions and responsive fallback; scroll/fixed regions; focus, selection, draft and reading-position retention; data/runtime/connection/permission sources; affected module IDs; and concrete browser acceptance paths. State whether the page is a documentation preview, fixture, or real service integration.
- For a **module**, declare: module ID and host pages; responsibility and controlled inputs/callbacks; reused exports or proposed additions; typography, spacing, color/token, borders, radius and alignment; hover/focus/selected/disabled/loading/error and applicable data/runtime states; collapsed/expanded and long-content behavior; keyboard/touch/reduced-motion/i18n behavior; side-effect owner and unknown-result recovery; and acceptance evidence. Include visible details such as selected Session styling, user-message appearance, phase dividers and action placement where applicable.
- Start a page change with its page declaration, then the affected module declarations. Start a module-only change with its module declaration and links to its host pages; update page declarations only where the layout or flow changes. Shared modules keep one contract with explicit variants, rather than separate conflicting specifications for each page.
- Record reference-version choices and conflicts explicitly. Preserve reference content when requested; explain which revision governs execution. Map reference colors to semantic tokens and declare any example-scoped size/style exception with its scope, reason and validation. Keep shared defaults unchanged unless the task explicitly includes changing the library contract. User instructions take precedence; making these declarations is part of the authorized work, not a new permission or confirmation gate.
- After implementation, verify both the mounted page and affected modules, including narrow containers, theme/locale changes, state recovery and cross-region navigation. Keep declaration status, UI/fixture completion, real-service verification and distribution validation separate. Update the declaration and execution checklist when the design changes; do not mark a design complete merely because it is documented.
