## 1. 目标与范围

将现有设计系统推进为可维护、可验证、便于渐进接入的组件库，同时建设 `/blog/` 优化展示页，让用户能阅读优化动机、实施方案、前后差异及可复核证据。

两条工作线同步推进：

1. 工程优化：按需加载、Canvas/长会话性能、受控布局、主题隔离、基础组件复用、文档一致性及发布质量。
2. 展示与反馈：用 Blog 记录每项优化的方案、实施状态、适用版本、前后效果、测试方法与已知限制。

本计划承接 [Canvas 建设计划](./canvas-design-system-plan.md) 与 [Canvas 实施记录](./canvas-implementation-log.md)，以当前已存在的 Canvas 为优化对象，不重新执行初始化。优化不得改变图文档、运行状态、审批、持久化、URL 和调用方权限语义。

当前工作区有进行中的国际化与其他改动。实施前重新检查差异，按文件/代码块合并，保留用户工作；本次计划不提交或推送这些改动。

## 3. 实施原则与依赖

- 按 Foundation → Primitive → Pattern → Workspace → Page 推进；新通用组件同步契约、示例、Catalog、Registry 和独立安装验证。
- 保留默认中文及英文 UI；复用 `lib/i18n-*`，站点内容使用独立资源。切换语言不重挂载编辑器、不清草稿、不产生服务写入。
- 先移除重复计算，再依据剖析结果决定窗口化、缓存或额外依赖；每个新增机制必须能说明解决的瓶颈。
- Blog 的文章、截图和历史报告属于站点，不加入便携组件的 Registry 依赖。
- 性能优化与视觉/行为优化分别验收。截图展示样式变化，基准报告证明耗时变化，真实服务回执证明业务结果。
- 第一批同时交付轻量组件目录、基础一致性修复、Blog 框架；后续优化逐项补文章和实测证据。

依赖顺序：M0 → M1 → M2/M3 → M4 → M5；M6 依赖 M2/M3，并按容量排期。M5 中通用 CI 可提前在 M1 建立，公开发布部分等待版本与许可证决策。

## 4. 优化任务与验收

- [x] 核对当前版本、dirty 状态和参考结论；记录实际测试清单，不延用“85 个测试”的历史数字。
- [x] 采集 `/components/`、`/dictionary/`、代表性详情页的生产构建网络资源、初始客户端 JS、Demo 挂载数量及首个共享控件可用时间；完整 TTI 尚未测量。
- [x] Canvas 固定 50/200/500/1000 节点及对应边数/拓扑；测量纯构图、首次可操作、选择到 Inspector 更新、连续拖动、内存与长任务。
- [x] Conversation/Activity 固定 1000/5000/10000 条记录，覆盖追加、原地更新、补历史、展开长内容及每秒多次流式更新。
- [x] 建立 Blog 内容 schema、优化 ID 和证据格式；先保存“优化前”截图与原始测量，防止改完后无法对比。

验收：每条基线包含源码版本/补丁标识、fixture、命令、浏览器/系统、视口、主题、语言、测量方法、样本数、结果及时间。未测项目标“待测”，共享主机异常记录为环境限制。

- [x] 对实际 background/surface/raised 上的小字号辅助文字测量 alpha 合成后的对比度，再修订 theme.css 与组件契约；不直接全局替换成固定 .5。
- [x] Dialog 统一使用 shadow-floating；检查浮层与常驻面板阴影用途。
- [x] 默认明确系统字体栈；若需要固定字体，另核对字体许可、离线构建及资源体积，避免仅为视觉一致引入运行时远程字体依赖。

**Blog 首版**

- [x] 按第5节实现索引、文章详情、证据展示、全站导航入口及首批内容。
- [x] 初始文章可发布“已公开的优化方案”，其实施状态保持 planned/measuring；未验证收益不显示提升百分比。

### M2 · Canvas 与长列表性能（P0）

**Canvas**

- [x] 在文档/定义/问题变化边界构建 nodeById、frameById、definitionByType、issuesByNodeId、edgesByNodeId，以及选中/折叠 ID Set。
- [x] 一次扫描边构建 fallback ports；hidden edge 通过两端索引查找；避免在每个节点中重复扫描整张图。
- [x] 分离结构、位置、选择与运行更新的依赖；不因单一选择改变重算连接规则和所有端口。
- [x] 保持未知类型节点、分组移动、折叠、重连、undo/redo、执行版本关联及多语言标签行为。缓存随实际输入变化失效，不仅依赖可能未变化的 revision。

**Conversation / Activity**

- [x] 用 ID Set/Map 消除 includes 嵌套扫描；保留原有去重语义：首次出现的位置、最新 payload。
- [x] 为高频更新增加可选显式 revision/变更提示；保留旧调用方兼容路径。不能只看数组长度或最后一条，需捕获历史消息修订、删除、重排与状态变化。
- [ ] 若基线证明 DOM 量为瓶颈，再引入可选窗口化，先验证动态高度、展开详情、焦点节点、文本选择和读屏可达性；不默认破坏浏览器全文查找/复制体验。
- [x] 跟随逻辑使用稳定消息 ID 和视口锚点；保留 64px 跟随阈值、未读提示、补历史锚点和手动返回最新。

验收：索引构建呈 O(N+E+I+D) 量级（I 为问题数，D 为定义数），具体交互收益以基准为准。至少同环境比较 200/500/1000 节点与 5000 条流式记录；编辑/日志行为回归通过后才写“已优化”。

### M3 · 受控布局、快捷键与基础交互（P0/P1）

- [x] WorkspaceShell 提供成对的 value/defaultValue/onChange 接口：sidebarCollapsed、Inspector 展开/宽度、底部面板展开/高度；明确桌面停靠与窄屏 overlay 是不同状态。
- [x] 保留非受控默认与宽度限制；受控模式由调用方回传值，回调不触发循环，不在 render 或响应式切换时写存储。
- [x] 提供示例适配器演示按 workspace/project ID 保存布局；组件本体不拥有 localStorage 或业务持久化；损坏/越界存储可恢复。
- [x] Canvas 复制、粘贴、全选、删除、撤销只在画布编辑上下文生效；普通文本 selection、Inspector、日志、输入和弹层保留原快捷键语义。
- [x] 优先提取已有重复的 Menu/Popover、Tabs/Segmented、Select/Combobox；Command Palette、Alert/Toast、Breadcrumb 依据调用点分批增加。
- [x] 迁移时区分导航、选值和动作菜单，补 Escape、方向键、触摸及焦点恢复；没有真实回调不显示“执行成功”。

验收：旧示例无修改或按明确兼容策略继续运行；受控/非受控双路径、项目切换、刷新恢复与坏数据均有覆盖；Canvas 外复制选中文本不会调用复制节点；中英文切换不重置布局与图。

### M4 · 低侵入主题与独立安装（P1）

- [x] 定义两种新安装方案：宿主兼容模式映射已有 shadcn token；独立模式使用带作用域的 `--eu-*` token 与 theme boundary。
- [x] 先完成 Button、Dialog、Canvas 和 RuntimeStatusBadge 的代表性验证，再迁移其他公开组件；主题核心定义仍集中维护，不复制两套手写色表。
- [x] 兼容模式不向宿主 :root 注入默认色；独立模式不覆盖宿主 --background/--primary，也不泄漏全局 reset、字体或容器尺寸。
- [x] Portal 内容继承对应主题 scope/变量；验证同页两个不同主题实例、浅/深色、Canvas 内部样式及 locale provider 组合。
- [x] 保留现有安装行为并标明 legacy 与迁移路径；切换默认安装模式随版本发布，禁止无说明地改变已有消费者样式。

验收：两个独立消费 fixture 均构建且浏览器操作通过；安装前后宿主区域 computed styles/截图一致；弹窗、菜单、画布不丢主题；Registry 不依赖站点或 Blog 文件。

### M5 · 质量门禁与可公开分发（P1）

- [x] CI 执行 lockfile 安装、lint、typecheck、i18n 校验、Webpack build、Playwright 及 Registry 安装检查；版本/浏览器固定，失败保留报告与 trace。
- [x] 对关键状态加视觉快照与自动无障碍检查；固定字体、视口、fixture、时钟及动效，只屏蔽真正不确定的区域；保留键盘/触摸人工验收。
- [x] 性能报告增加明确回归门槛，区分稳定 CI 与共享主机观测；保存失败原始数据，复测不能覆盖首次失败。
- [ ] 确定许可证选择并检查第三方资源归属后，再添加 LICENSE；选择未确认时保留为发布阻塞项，不代替项目所有者决定许可条款。

- [x] 高频“添加”与运行能力按上下文突出，区域内最多一个 Primary；撤销/查找作为辅助，JSON/帮助进入可发现菜单。

## 5. Blog 展示页建设方案

### 5.1 用户任务与信息架构

Blog 的名称建议为“优化日志 / Engineering Blog”。用户需要找到相关优化、理解方案、查看效果、定位证据，并跳转当前组件或演示。

| 页面/区域       | 内容与交互                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------- |
| `/blog/`        | 简介、搜索、分类、实施状态筛选、按更新日期排序的文章列表；URL 保留筛选/搜索，返回后恢复     |
| `/blog/<slug>/` | 标题、摘要、发布日期/更新日期、作者、优化 ID、适用版本、实施状态、目录、正文、相关文档/演示 |
| 方案区          | 当前问题 → 基线证据 → 设计/技术方案 → 兼容影响 → 实施步骤                                   |
| 效果区          | 前后截图、固定字段指标表、按需交互演示；目标/实测/未测清楚区分                              |
| 验证区          | 方法、环境、样本、版本、报告下载、测试范围、限制与失败项                                    |
| 延伸区          | 关联组件文档、优化计划、Changelog、当前 Demo、相关文章                                      |

页面草图：

```text
全站 Header · Blog
优化日志                         搜索方案
全部 / 性能 / 设计一致性 / 复用 / 分发 / Canvas
实施状态筛选                     按更新时间
─────────────────────────────────────────
标题 + 摘要                      状态
OPT 编号 · 分类 · 日期 · 适用版本    阅读方案 →
─────────────────────────────────────────

文章页：正文约 72ch + 桌面右侧目录
问题 → 方案 → Before / After → 指标 → 验证与限制
窄屏：单列正文，目录与前后对比纵向展开
```

默认采用 Item/文章列表与分隔线。截图比较可用独立预览区域，不把每段文字包进 Card。复用 SiteFrame/Header、Button/Input/Badge/Tag/Chip/DataRegion；文章状态是内容元数据，不使用 RuntimeStatusBadge。

### 5.2 内容与证据模型

首版使用版本管理中的类型化内容与结构化正文块，避免引入 CMS、数据库、评论、订阅或任意 MDX 执行。正文块支持段落、标题、列表、代码、图片、对比、指标表和演示链接；后续需要 Markdown 作者体验时再增加受约束编译链。

| 模型        | 必须字段/规则                                                                                                  |
| ----------- | -------------------------------------------------------------------------------------------------------------- |
| BlogPost    | slug、title、summary、author、publishedAt、updatedAt、tags、optimizationIds、relatedComponents、body           |
| 内容可见性  | draft / published；draft 不进入公开静态导出、搜索、sitemap 或 feed                                             |
| 实施状态    | planned / implementing / measuring / verified；与文章是否 published 独立                                       |
| 版本关联    | baselineVersion、resultVersion 或 sourceSnapshotId；未提交改动需可追溯补丁标识，不能只写 HEAD                  |
| 翻译        | 原文语言与可选译文分开；UI 中英资源完整，无英文正文时展示原文及提示，不假装已翻译                              |
| Comparison  | before/after 资源、说明、alt、主题、语言、视口、fixture、采集版本；缺少一侧时显示“待补充”                      |
| Metric      | key、label、unit、direction、before、after、target、statistic、sampleCount、evidenceId；未知值为 null，显示“—” |
| Evidence    | 类型、文件/URL、时间、环境、命令、版本、样本、原始结果；对外只发布审核后的静态资源                             |
| Limitations | 未测场景、适用范围、退化、失败或环境限制；局部通过不代表整体 verified                                          |

指标变化只在单位、fixture、环境和统计口径匹配时计算；基线为零或数据缺失时不显示百分比。耗时下降使用 `(before-after)/before`，吞吐上升反向计算；回归如实显示，不统一染绿。

历史文章保存不可变的摘要/截图/报告；“打开当前 Demo”显式标为当前实现。需要历史交互时后续使用版本化静态快照，不在主站客户端同时打包多个历史组件实现。

### 5.4 路由、静态导出与国际化

当前 `next.config.ts` 使用 `output: "export"`、`trailingSlash: true`。Blog 沿用静态部署：

- 构建时枚举 published slug，使用 `generateStaticParams` 生成文章详情；未知 slug 返回 404。
- 文章正文和 metadata 在服务端构建，搜索/筛选及按需演示使用小型客户端组件；搜索索引仅包含标题、摘要、标签等必要数据。
- 查询字符串由客户端读取并同步，兼容静态导出；按安装版本指南处理所需 Suspense 边界，不用请求期服务端搜索。
- 标题、description、canonical、静态分享图、sitemap/可选 feed 指向配置后的 siteUrl；发布检查拒绝 localhost canonical。
- 沿用当前无语言路由约定，默认静态中文 HTML；页面 UI 支持英文，正文按已有翻译切换或提示原文。单 URL 不宣称有两个独立语言的搜索引擎页面。
- 增加 Header Blog 入口时验证移动端滚动/换行和导航焦点，避免挤压现有入口；Blog 不使用 Canvas 的全窗口特殊布局。

## 6. 测量预算与质量门禁

以下是拟定目标，M0 后结合基线环境固定阈值并保留变更记录，不是当前结果。

| 维度               | 验收目标                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| 目录/Blog 默认加载 | 无隐藏重型 Demo 挂载；不加载 Canvas 引擎；加载依赖通过网络请求与 bundle 边界共同检查             |
| 页面客户端体积     | 同口径记录压缩传输字节和解析成本；先证明移除依赖，再制定字节预算，不承诺未经测量的降幅           |
| Canvas             | 沿用 200 节点可操作≤2s、Inspector p95≤100ms、拖动≥30fps 的暂定目标；500/1000 节点先记录容量边界  |
| 性能回归           | 稳定环境使用基准对照、多轮样本；建议 p95 退化超过20%且越过绝对预算时阻断，环境异常单列复核       |
| 消息追加           | 高频更新不序列化全部正文；补历史/展开不丢锚点；目标 5000 条样例追加到可见更新 p95≤100ms，M0 校准 |
| 可读性             | 正常小字号文本按 AA 目标逐组合验证，状态不只靠颜色；禁用/装饰与可阅读元信息分开                  |
| Blog 可信度        | verified 必须带适用版本、验证范围与证据；未测值不能为0，缺资源/重复 slug/缺必要 alt 阻止构建     |

建议每个候选版本至少3轮、每轮不少于30次选择/追加样本，报告 median/p95 与离散程度；冷启动单独多次新上下文采集。交互测量起点与“内容实际可用”终点固定，不把 DOM 数量变化直接当作渲染完成。Canvas 拖动同时采集位置变化/长帧与 rAF 数据，不只统计脚本发出事件的频率。

## 8. 完成标准与下一步

每个优化任务交付四项：实现与兼容说明、自动/人工验证、可复核前后证据、对应 Blog 更新。仅完成文章或截图不算工程优化完成；仅通过 fixture 不算真实服务验收完成。

M0–M4 与 M6 已按非 Canvas 优先、Canvas 最后的顺序完成实现，Blog 已发布六篇本地静态文章。M5 的质量流程与版本快照工具已实现，远程 CI 与公开发布未执行。页面完整 TTI、原生查找界面和读屏人工验收仍待补齐；共享主机上的 Canvas 冷启动与长会话追加没有达到全部暂定目标。

实施时仅在需要实际发布前收敛公开域名/托管目标、许可证及不可变版本策略；这些决策不阻塞本地优化和 Blog 页面建设。
